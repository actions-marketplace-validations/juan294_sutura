# Repair transaction shapes

What one Sutura repair attempt may change, and what it refuses. Source:
`packages/core/src/engine/repair-targets.ts` and `dependency-transaction.ts`.

## Supported shapes

| Shape | What changes | How the pair is established |
| --- | --- | --- |
| Single source | One controller-selected excerpt | The existing one-slot proposal contract |
| Related source pair | Two supplied editable sources | A resolved import relationship between them, unambiguous within the bounded source closure |
| Manifest and lockfile | The root `package.json` plus its `pnpm-lock.yaml` | Node runtime only; the lockfile is generated by the pinned package manager, never by the model |

The model names controller-supplied slot identifiers. It cannot choose a path,
a line range, or how many slots exist, and a reply that adds, drops, repeats or
renames a slot is refused rather than partially applied.

## Bounds

- **Two changed files total**, including any generated artifact. The effective
  cap is the stricter of two and the repository policy's `maxChangedFiles`, so a
  policy can lower it and never raise it.
- At most two pair candidates join the existing bounded single-file search.
- A Phase 2 controller grant is still required for any conventional test or
  tool-configuration path. A second file does not widen a grant.

## Not supported, and what happens instead

Each of these produces an explicit abstention, never a partial transaction:

- A migration needing source, manifest and lockfile together, or any third
  changed path.
- File creation, deletion or rename inside a transaction.
- An unrelated or ambiguously resolved file pair.
- A nested (non-root) manifest, a manifest without its lockfile, a non-Node
  runtime, or any package manager other than the repository's pinned pnpm.
- A dependency change that is not exactly one existing package moving between
  pinned releases: ranges, dist tags, aliases, `workspace:`, `file:`, URL and
  git specifiers, added or removed dependencies, and more than one change.
- Any manifest edit outside the dependency sections, which is what keeps a
  lifecycle script, registry override or package-manager pin from riding along
  with a version bump.
- A generated lockfile that is not byte-identical across two resolutions, is
  empty, exceeds the artifact byte bound, or references an origin outside the
  approved registry list.

## Dependency resolution boundary

The network-capable resolution lane receives the candidate manifest and nothing
else. Repository source and model-authored commands cannot reach it, scripts are
disabled, and the repair and audit branches stay network-disabled. Failure to
establish that separation is an abstention, not an exception.

## Evidence status

The supported shapes are proved by offline fixtures and unit controls:
`repair-two-file-export-contract` and `python-repair-two-file-call-contract`
fail after either partial patch and pass only as a complete transaction, with
hidden preservation checks agreeing. No live migration, repair-rate or cost
claim follows from these; phase 10 owns authorized provider measurement.
