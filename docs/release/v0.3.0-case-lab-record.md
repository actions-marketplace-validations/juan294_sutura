## Incident 1: `deploy()` linked the wrong Vercel project

`vercel pull --yes --environment=production` from a fresh checkout with no
`.vercel` link silently created a brand-new, empty project named `case-lab`
(auto-named from the directory) instead of linking to the real, 9-day-old
`sutura-case-lab` project that owns the `sutura-case-lab.vercel.app` domain.
The build was correct; the deploy just went to the wrong place. `deploy()`'s
own health-check verification caught the mismatch and refused rather than
reporting false success — no live regression, but a stray project existed
briefly.

**Fix** (commit `0b7a5a3`): `deploy()` now runs `vercel link --yes --project
sutura-case-lab` first and refuses, before any build or deploy call, unless
`packages/case-lab/.vercel/project.json`'s `projectName` is exactly
`sutura-case-lab` — fail-closed the same way the post-deploy health check
already is. The stray `case-lab` project was deleted
(`vercel project rm case-lab --scope thecreativetoken`) after the retried
deploy confirmed the real project serves v0.3.0.

## Incident 2: live dispatches fail to publish (v0.3.0 regression)

The Phase 5 smoke dispatch (`javascript-repair`, request `cl-1789480072251-87a2398a`,
[sutura-demo run 34977342282](https://github.com/juan294/sutura-demo/actions/runs/34977342282))
ran the repair successfully but failed at "Publish the public-safe result
document": `replay bundle actionSha c94eee2086b31450d975137a0102dda18522d0b8
must equal the demo commit f8ea06f211163a5bc233dfadf1c728d4c79b7418`.

Root cause: commit `9d774a1` (2026-09-14, "fix: stabilize dogfood runtime
telemetry") changed the Action's identity resolution
(`resolveActionIdentity` in `packages/action/src/terminal-failure.ts`) to
check `GITHUB_ACTION_REF` first. Since `case-lab.yml` invokes the Action via
`uses: juan294/sutura/packages/action@<sha>`, `GITHUB_ACTION_REF` is always
the pinned Action commit — so a replay bundle's `actionSha` is now the
Action's own commit (unified with `release.actionSha` and the controller per
Phase 3), never the calling `sutura-demo` repo's own commit. The check
comparing it against the demo commit was correct for the v0.2.0 Action but
is a v0.3.0 regression: **no live dispatch through the public Case Lab has
been able to publish a result since the v0.3.0 Action shipped.** It went
undetected because the case-lab test suite only exercises committed replay
fixtures (self-consistent by construction) and no real live dispatch had
happened through this exact path since `9d774a1` landed — today's smoke test
is what caught it, which is exactly what it's for.

**Fix** (commit `a278812`, on `develop`): `publishResult()` and
`replayedResult()` now compare `bundle.actionSha` against `release.actionSha`
in all three bindings (`publish.ts`, `replay.ts`, `replay/README.md`).
`packages/action` is untouched — the new resolution order is correct, and
`scripts/release-evidence.mjs`'s `verifyDogfoodStreak` depends on it.

**This fix does not reach the public live path until v0.3.1.**
`publish-result` runs from `.sutura` at `SUTURA_CONTROLLER_SHA` inside
`sutura-demo`'s `case-lab.yml` (currently pinned to `c94eee20…`, v0.3.0), and
the gate wired in Phase 5 requires the controller to be the newest tag —
merging the fix to `develop` doesn't move that pin. The next release cycle
(v0.3.1) carries the fix through `### 8a`.

**Live runs disabled today**: `CASE_LAB_ENABLED` set to `false` in the
`sutura-case-lab` Vercel production environment (env-only, reversible;
propagated via a redeploy, since Vercel bakes env vars into the build rather
than reading them from a live store per request despite the code comment
suggesting otherwise). Deterministic results stay up. Re-enable as part of
the v0.3.1 cycle once the fix is live.

## Follow-ups

1. **Replay-engine determinism for `gave-up` bundles — fixed 2026-09-15 (validation follow-up on `develop`).**
   The real bundle from the smoke dispatch (`sutura-demo` run `34977342282`,
   artifact `sutura-replay-34977415599.json`) is complete and correctly
   `actionSha`-bound, but replay diverged at exchange 17 (`updateCheckRun`):
   the live Action attached a `test-assertion` annotation derived from the
   checkout's git object store (`packages/core/src/github/checks.ts`
   `checkAnnotations`), which no replay has. Root cause: the port cursor
   compared the check-run arguments including `annotations`. Fix:
   `packages/core/src/replay/replay-github.ts` normalizes `annotations` out of
   `updateCheckRun` on both the recorded and the replayed side; conclusion,
   title and summary are still compared exactly. The bundle is committed as
   `packages/case-lab/src/__fixtures__/live-34977342282-javascript-repair-gave-up.json`
   (public-safe; SHA-256 `87fc79306bcec3656fef6754366f3dd311d2d52b102df20e060d3285e0e4b336`)
   and drives two named tests: the `gave-up` replay in
   `packages/case-lab/src/replay.test.ts` and the release-bound `actionSha`
   guard in `packages/case-lab/src/publish.test.ts`, which satisfies both
   `.claude/rules/ci-parity.md` obligations for this incident.
2. **Live `gave-up` vs. benchmark `fixed` for `javascript-repair` — open.**
   Evidence from the replayed bundle: all 15 sandbox `run` operations
   completed normally (exit codes 0/1, no executor errors); the search applied
   patches on four branches but the diagnosed test kept failing with the same
   error fingerprint and the run ended on `Branch terminal: repeated-state`
   → `gave-up` with zero race candidates. So this is proposal/search quality
   on the demo path, not infrastructure. The
   v0.3.0 benchmark fixed `repair-off-by-one` (`javascript-repair`) cleanly
   at the same commit (`docs/demo/placebo-v0.3.0-live-2026-09-15.json`), but
   today's live dispatch through the public demo path gave up. The demo path
   differs from the benchmark path (runtime, budgets, PR flow) — this is the
   flagship case for Friday's launch, so investigate from the downloaded
   bundle before v0.3.1, separately from the publish-path fix above. Also
   for the launch narrative: the v0.3.0 evidence records `upstream-incident`
   as `gave-up` in both Tavily arms, so the Case Lab will show it as not
   matching expectation.
