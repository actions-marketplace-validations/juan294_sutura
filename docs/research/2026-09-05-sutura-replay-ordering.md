## 0. Answer in three paragraphs

The replay matcher is a **strict positional cursor**, not a content-addressed index.
`RecordedCallCursor.next()` at `packages/core/src/replay/recorded-call-cursor.ts:38`
takes `this.records[this.index]` and asserts that the live call's method and canonical-JSON
arguments equal that record's. It never searches for a matching record. The `$[0]` in the error is
the first element of the executor call's argument array, which for
`run(parent, cmd, options)` is the **parent ImageId**
(`packages/core/src/replay/replay-executor.ts:39-41`).

The recorded executor stream is not deterministic because the adaptive search expands branches
**concurrently** through `Promise.all` at
`packages/core/src/engine/search.ts:122`, and each branch's executor
calls are issued *after* that branch's provider response arrives. In a live run the provider
latencies order those calls; in replay every provider response resolves from memory, so the branches
run in lockstep microtask order instead. The two live bundles on disk prove the divergence is real
and not hypothetical: they are two runs of the *same case* and they recorded two *different*
interleavings of the same six calls (§3.2).

Image ids are **not** the problem. Every image uuid is generated by the ConTree service
(`packages/core/src/executor/contree.ts:583-590`) and `RecordedExecutor`
returns the recorded value verbatim, so under replay the ids in flight are byte-identical to the
recorded ones. Nothing needs renaming. The only defect is *which recorded record is consumed at
which position*. That makes option (a) — a canonical request fingerprint plus first-unconsumed-match —
the right shape of fix, and it is unusually cheap here because every concurrent-phase executor call
already carries a deterministic `operationId` such as `search-001-op-002` (§7).

## 1. The replay bundle format

### 1.1 Schema

`packages/core/src/replay/bundle.ts:15`

```ts
export const REPLAY_BUNDLE_SCHEMA_VERSION = 'sutura-replay-v1' as const;
```

Caps, `bundle.ts:17-20`: `MAX_BODY_BYTES = 1 MiB`, `MAX_HTTP_EXCHANGES = 512`,
`MAX_PORT_CALLS = 256`, `MAX_EXECUTOR_CALLS = 512`.

The bundle type is at `bundle.ts:132-149`: `schemaVersion`, `runId`, `repo`, `actionSha`,
`capturedAt`, four recorded streams (`github`, `repository`, `executor`, `http`), `configuration`,
`completeness`, and an optional `outcome`.

An executor record, `bundle.ts:111-116`:

```ts
export interface RecordedExecutorCall {
  sequence: number;
  method: keyof Executor;
  args: unknown[];
  result: unknown | RecordedError;
}
```

So an executor exchange stores **only** an ordering index, the method name, the positional argument
array, and the result. There is no request key, no hash, no branch id, no timestamp.

### 1.2 Where executor exchanges are recorded

`packages/core/src/replay/record-executor.ts:5-67` —
`recordingExecutor(executor, recorder)` wraps the `Executor` port. Every method follows the same
shape (`record-executor.ts:9-27`):

```ts
const sequence = recorder.reserveExecutorSequence();   // line 14 — at CALL START
try {
  const result = await operation();
  recorder.recordExecutor({ method, args, result }, sequence);   // line 17
  return result;
} catch (error) {
  recorder.recordExecutor({ method, args, result: recordedErrorResult(error) }, sequence);
  throw error;
}
```

The six wrapped methods and their recorded `args` (`record-executor.ts:29-66`):

| method | recorded `args` |
| --- | --- |
| `importImage` | `[ref]` |
| `snapshot` | `[dir, base, options]` |
| `run` | `[parent, cmd, options]` |
| `runMany` | `[parent, commands, options]` |
| `operationCapacity` | `[]` |
| `cancel` | `[operationId]` |

The **sequence is reserved before the await** (`bundle.ts:437-459`,
`ReplayRecorder.reserveExecutorSequence` → `reserveSequence`), so `sequence` is *issue order*, not
completion order. `recordExecutor` (`bundle.ts:533-555`) then writes the record under the reserved
number once the call settles. `finish()` sorts each stream by sequence
(`bundle.ts:623-626`) — a stable re-sort, never a renumbering.

`packages/action/src/main.ts:137-139` is the live wiring:

```ts
const executor = recorder ? recordingExecutor(baseExecutor, recorder) : baseExecutor;
```

`baseExecutor` is the `ContreeExecutor` (`main.ts:129`). Note that the ConTree HTTP traffic is
*also* recorded (`recordingContreeFetch`, `main.ts:134`) into `bundle.http` with
`boundary: 'contree'`, but replay never consumes it — `replay-orchestrate.ts:86` filters it out,
because `RecordedExecutor` replaces the sandbox at the logical port instead. `ContreeExecutor`'s own
internal `Promise.all` over `runMany` (`contree.ts:266`) is therefore below the recording boundary
and irrelevant: one `runMany` is one record.

### 1.3 Validation invariants

`packages/core/src/replay/validate.ts:333-345` (`assertSequenceDomain`),
applied per domain at `validate.ts:504-506`:

- sequences must be duplicate-free (`validate.ts:339-341`);
- when `completeness.complete` is true, the sorted sequence set must be exactly `1..N` with no gaps
  (`validate.ts:342-343`, message `bundle.executor sequence is incomplete`).

Domains: `[...github, ...repository]` share one numbering space ("port"); `http` is one space
including `contree`; `executor` is its own. Any redesign must preserve contiguity or change this
check.

## 2. The replay executor and the exact error

### 2.1 Wiring

`packages/core/src/replay/replay-orchestrate.ts:80-99`:

```ts
const portCursor = new RecordedCallCursor<RecordedPortCall>(
  [...validated.github, ...validated.repository], describeMethodCall, 'port');       // :80
const httpCursor = new RecordedCallCursor<RecordedHttpExchange>(
  validated.http.filter(({ boundary }) => boundary !== 'contree'),
  (exchange) => ({ method: exchange.boundary, args: [] }), 'HTTP');                  // :85
const executorCursor = options.executor === undefined
  ? new RecordedCallCursor(validated.executor, describeMethodCall, 'executor')       // :91
  : undefined;
const executor = options.executor ?? new RecordedExecutor(
  validated.executor, (args) => repository.normalizeArgs(args), executorCursor);     // :95
```

`replay-orchestrate.ts:146` calls `assertConsumed()` on every cursor after `orchestrate` returns;
`:149` calls `rethrowMismatch()` on the error path.

### 2.2 How a call is matched — strictly by position

`packages/core/src/replay/recorded-call-cursor.ts:33-66`:

```ts
next(method, args, normalizeArgs = (v) => v): T {
  const record = this.records[this.index];                       // :38  positional
  if (!record) { ... 'sequence exhausted' ... }                  // :39-46
  this.index += 1;                                               // :48
  const expected = this.describe(record);
  if (expected.method !== method) {                              // :50
    return this.fail(new ReplayMismatchError(record.sequence, '$.method', expected.method, method));
  }
  const normalized = normalizeArgs(args);
  if (canonicalJson(expected.args) !== canonicalJson(normalized)) {          // :56
    const difference = firstJsonDifference(expected.args, normalized);       // :57
    return this.fail(new ReplayMismatchError(
      record.sequence, difference?.path ?? '$.args', difference?.expected, difference?.actual));
  }
  return record;
}
```

Constructor sorts by `sequence` (`:30`). There is no lookahead, no keying, no per-caller partition.

`RecordedExecutor` (`packages/core/src/replay/replay-executor.ts:25-53`)
calls `this.cursor.next(method, args, this.normalizeArgs)` and then
`throwRecordedErrorResult(call.result)` so recorded failures re-throw. Its `run` is:

```ts
run(parent: ImageId, cmd: string, options?: RunOptions): Promise<RunResult> {
  return Promise.resolve(this.next<RunResult>('run', [parent, cmd, options ?? null]));   // :39-41
}
```

`normalizeArgs` is `RecordedRepository.normalizeArgs`
(`packages/core/src/replay/replay-repository.ts:76-96`), which only
rewrites temporary checkout directory strings to `checkout-N`. It does nothing to image ids.

### 2.3 The exact code that produces `Replay exchange 14 differs at $[0]`

Three pieces:

1. **Message text** — `packages/core/src/replay/replay-error.ts:8-11`:

```ts
super(`Replay exchange ${sequence} differs at ${path}: expected ${JSON.stringify(expected)}, received ${JSON.stringify(actual)}`);
```

2. **`sequence: 14`** — the `record.sequence` of the 14th executor record
   (`recorded-call-cursor.ts:58`).

3. **`path: '$[0]'`** — `firstJsonDifference`
   (`packages/core/src/replay/canonical-json.ts:41-71`) is called with
   the two **argument arrays**, root path `'$'`. Both are arrays, so it descends to index 0
   (`canonical-json.ts:47-55`) and reports `$[0]`. For `run`, `args[0]` is the parent `ImageId`.

`replay-executor.test.ts:22-27` is the existing unit test that pins this message shape
(`expect(() => executor.importImage('node:20')).toThrow(/\$\[0\]/u)`).

## 3. The source of nondeterminism

### 3.1 The concurrency primitive

`packages/core/src/engine/search.ts:111-151`:

```ts
const concurrency = Math.max(1, Math.floor(options.concurrencyCapacity?.() ?? parents.length));  // :111
...
const batch = parents.slice(start, start + Math.min(concurrency, authorizedBatchSize));          // :115
const controllers = batch.map(() => new AbortController());                                      // :116
const settled = batch.map(() => false);                                                          // :117
const expansions = await Promise.all(batch.map(async (parent, index) => {                        // :122
  ...
  const expansion = await options.expand({ parent, parentImageId, depth, branch, nodeId, operationId, signal });  // :129
  settled[index] = true;                                                                          // :138
  const passed = expansion.policyEvidence.valid && expansion.testEvidence.exitCode === 0 && expansion.candidate !== undefined;
  if (!cancellationStarted && passed) {                                                            // :142
    cancellationStarted = true;
    await Promise.all(ids.flatMap((otherId, otherIndex) => {                                       // :144
      if (otherIndex === index || settled[otherIndex]) return [];
      controllers[otherIndex]!.abort();
      return options.cancel === undefined ? [] : [options.cancel(otherId)];
    }));
  }
  return expansion;
}));
```

Concurrency is enabled from `heal.ts`
(`packages/core/src/heal.ts:976-981`):

```ts
concurrencyCapacity: () => ctx.search === undefined
  ? 1
  : Math.max(1, Math.min(
      providerCapacityAvailable(providerCapacity),
      ctx.executor.operationCapacity().available,
    )),
```

So concurrency is 1 only when `search` is unset. Every captured live bundle sets
`configuration.search = {initialBranches: 4, beamWidth: 2, maximumDepth: 4, maximumTotalBranches: 12}`,
and every bundle records `operationCapacity() => {limit: 40, active: 0, available: 40}`. The
fan-out is 4.

`expand` is `heal.ts:1009-1123`. Inside it, `runControlledRepairAttempt` (`heal.ts:1020`) drives the
provider turn and then the tool calls; the executor calls come out of
`packages/core/src/engine/repair-tools.ts:156-175`:

```ts
private async run(command, parent = this.current.editableImageId, maximumTimeoutSec = MAX_TOOL_TIMEOUT_SEC) {
  this.options.budget.reserveSandboxOperation();
  const timeoutSec = Math.min(maximumTimeoutSec, Math.max(0.001, this.options.budget.remainingElapsedTimeSec()));  // :162-165
  this.operationIndex += 1;                                                                                        // :166
  const operationId = this.options.operationIdPrefix === undefined
    ? undefined
    : `${this.options.operationIdPrefix}-op-${String(this.operationIndex).padStart(3, '0')}`;                       // :167-169
  if (operationId !== undefined) this.options.onOperationStart?.(operationId);
  return this.options.executor.run(parent, command, { cwd: '/workspace', timeoutSec, ...(operationId === undefined ? {} : { operationId }) });
}
```

`operationIdPrefix` is the search `nodeId` (`heal.ts:1045`, `repair-attempt.ts:425`), so a branch's
executor calls are labelled `search-001-op-001`, `search-001-op-002`, and so on.

The tool sequence per branch is `apply_patch` → `run_test` → `submit_candidate`
(`packages/core/src/engine/repair-attempt.ts:453,461,474`), i.e. two
executor `run` calls per branch, the second parented on the image the first produced
(`repair-tools.ts:402` then `repair-tools.ts:369` via `this.current.editableImageId` updated at
`repair-tools.ts:411-415`).

Other concurrency-adjacent executor call sites:

- `heal.ts:947-963` `availableBranches` calls `ctx.executor.operationCapacity()` (`:953`) — invoked
  by the scheduler at `search.ts:105` and `search.ts:113`, and **from inside a concurrent branch** at
  `heal.ts:1051`.
- `heal.ts:982-1001` `cancel` calls `ctx.executor.cancel(activeOperation)` (`:991`), driven by the
  race at `search.ts:144`.
- `heal.ts:1062-1075` the abort path calls `ctx.executor.cancel(lastOperation)` (`:1065`).

Non-concurrent executor call sites (serial, before or after the search): `heal.ts:508` `snapshot`,
`heal.ts:526` `prepareDependencies`, `heal.ts:544` `snapshot`, `heal.ts:557` `run`,
`heal.ts:1342` `importImage`, `heal.ts:1361` `run` (reproduction),
`packages/core/src/engine/triage.ts:62` `runMany`,
`packages/core/src/engine/repair.ts:630` `runMany`.

`packages/core/src/runtime/python.ts:130` also uses `Promise.all`, but
over file reads, not executor calls.

### 3.3 A second, smaller clock dependency

`repair-tools.ts:162-165` computes `timeoutSec` from `budget.remainingElapsedTimeSec()`
(`packages/core/src/engine/repair-budget.ts:146-150`, which reads
`Date.now()`). In practice this is clamped to the constants `MAX_TOOL_TIMEOUT_SEC = 30` and
`MAX_TEST_TIMEOUT_SEC = 120` (`repair-tools.ts:24-25`), and all recorded live options show exactly
`30` or `120`, so it is stable. It becomes a mismatch source only for a run within ~30 s of the
600 s elapsed budget, where `remaining` would win the `Math.min`. Worth guarding, not the current
failure.

## 4. Do the LLM/HTTP exchanges have the same problem?

**Yes, structurally identical — they are positional, not content-keyed.**

`packages/core/src/replay/replay-fetch.ts:122-129`:

```ts
const fetch = async (input, init) => {
  const exchange = cursor.next(boundary, []);   // :126  positional; args are EMPTY
  assertRequest(exchange, input, init);         // :127  content check AFTER selection
  return recordedResponse(exchange);
};
```

The cursor's `describe` for HTTP is `(exchange) => ({ method: exchange.boundary, args: [] })`
(`replay-orchestrate.ts:87`). So the cursor keys on **boundary name only** (`'nebius'` vs
`'tavily'`) and position. `assertRequest` (`replay-fetch.ts:43-73`) then verifies method, exact URL
string, and canonical-JSON body equality against the record the cursor already chose. There is no
hashing and no lookup by content.

Two consequences worth flagging:

1. **The HTTP boundary survives the fan-out only by accident.** Sequence numbers are reserved at
   *issue* time and the `Promise.all` fan-out at `search.ts:122` starts branches eagerly in array
   order, so the first provider call of each branch is issued in a deterministic order. It is the
   executor calls, which happen *after* each branch's response resolves, that inherit latency
   ordering. The moment a branch makes a *second* provider call (the invalid-JSON retry at
   `packages/core/src/engine/repair-attempt.ts:389`), HTTP issue order
   also becomes latency-dependent and the same class of failure appears on the provider boundary.
   That is consistent with `replay-orchestrate.test.ts:160-164`, which pins run `33323765566`
   failing at HTTP sequence 108 with `sequence exhausted`.

2. **HTTP content mismatches are unrecoverable and can be silently swallowed.** `assertRequest`
   throws `ReplayMismatchError` *directly* (`replay-fetch.ts:49,53,66`), not through
   `RecordedCallCursor.fail`, so `this.mismatch` is never set and `rethrowMismatch()` at
   `replay-orchestrate.ts:149` cannot resurface it. Callers that wrap provider errors then mask it.
   Verified empirically: replaying either live bundle with the `develop` build of core yields

   ```
   ERROR name= ClassificationError
   message= Diagnosis model request failed
   ```

   which comes from `packages/core/src/diagnose/classify.ts:198-202`:

   ```ts
   try { reply = await llm.chat('nano', messages, options); }
   catch { throw new ClassificationError('Diagnosis model request failed'); }
   ```

   The underlying `ReplayMismatchError` (prompt drift between `develop` and the released action)
   is discarded. This is why the executor-14 failure is only visible with the *released* CLI whose
   `actionSha` matches the bundle — on `develop` an earlier provider mismatch hides it. It is also a
   real diagnosability defect independent of the ordering work.

For completeness: replaying the develop-era fixture `33325938237` with the built core gives
`Replay exchange 92 differs at $: expected "recorded HTTP call", received "sequence exhausted"` —
the same provider-drift class, not the executor class.

## 6. Constraints on any fix

1. **Schema version.** `sutura-replay-v1` (`bundle.ts:15`). Adding a field to
   `RecordedExecutorCall` means either a `v2` or a strictly optional field, because
   `parseReplayBundle` validates each record's keys loosely (`validate.ts:313-331` checks
   `sequence`, `method`, `args`, `result` but does not reject extra keys on executor records — unlike
   `parseCapturedFixturesManifest`, which does reject unknown keys at `manifest.ts:72-73`). An
   additive optional field on executor records is therefore backward-compatible with the current
   validator, but old bundles will not carry it, so the matcher must work without it.

2. **Sequence contiguity.** `validate.ts:342-343` requires `1..N` with no gaps for a complete
   bundle. A matcher that consumes out of order does not violate this — contiguity is a property of
   the stored array, not of consumption order. No change needed if the fix is consumption-side only.

3. **Bundle content hash.** `bundleSha256` is computed over the **entire serialized fixture file**,
   not over the `bundle` object: `packages/case-lab/src/cli.ts:241-243`
   (`JSON.stringify(fixture) + '\n'`, then SHA-256) and re-derived on read at
   `packages/case-lab/src/replay.ts:201-204`. It is only
   format-validated downstream (`packages/case-lab/src/result.ts:68,461`).
   Captured action fixtures are separately bound to their manifest SHA by
   `scripts/captured-fixtures.test.mjs:96`. **Consequence: any change
   that rewrites bundle bytes invalidates every recorded hash.** A consumption-side fix that does
   not touch stored bundles avoids this entirely.

4. **Completeness check.** `bundle.ts:597-616` (`finish`) and `validate.ts:486-503`. Requires
   `github`, `repository`, `executor`, `nebius`, and `contree` streams all present and non-truncated.
   Order-independence does not interact with it.

5. **Consumers that depend on exchange order.** Searched and confirmed: **none outside core's own
   replay machinery.**
   - Case Lab (`replay.ts:140-191`, `cli.ts:210-257`, `publish.ts:64-70`, `pin.ts`,
     `acceptance.ts`) treats the bundle as opaque, checking only `actionSha`,
     `completeness.complete`, and `outcome`.
   - The evaluation/ATIF export (`packages/evaluation/src/atif.ts:29-112`)
     consumes `TraceEvent[]` from the `EvaluationManifest`, a **separate** schema with its own
     `sequence`. Case Lab's replay path even strips `.trace`
     (`packages/case-lab/src/replay.ts:84-89`).
   - `scripts/replay-contract.mjs` and `scripts/captured-fixtures.test.mjs`
     delegate to `parseReplayBundle` and otherwise compute order-agnostic boundary sets.
   - `scripts/capture-run.mjs:333` assigns `sequence` for the `github`
     stream it builds itself; it merges `http`/`executor` from the action artifact without
     re-sequencing (`:397-414`).
   - `scripts/verify-bundle.mjs` is unrelated (it checks the committed
     `packages/action/dist/index.cjs`).

6. **Public API surface.** `RecordedExecutor`, `replayBundle`, `ReplayMismatchError`,
   `parseReplayBundle`, `canonicalJson`, `firstJsonDifference` are all exported from
   `packages/core/src/index.ts:165-186,285-303`.

7. **Documentation.** No doc states an ordering guarantee in prose. The closest are
   `packages/case-lab/replay/README.md` (fixture shape; partial bundles
   refused) and `docs/research/2026-09-04-sutura-case-lab.md:78-96`
   (schema, caps, completeness, and the note that two of the three complete bundles no longer replay
   because request shapes drifted). The ordering rule exists only as executable code.

## 7. Options for order-independent matching

### Which ids come from where

This decides whether any renaming is needed. It is not.

| Value | Origin | Stable under replay? |
| --- | --- | --- |
| image uuid (`importImage`/`snapshot` result, `RunResult.imageId`) | ConTree service, `contree.ts:583-590` (`result_image_uuid`) | **Yes** — `RecordedExecutor` returns the recorded string verbatim, so replayed ids are byte-identical to recorded ids. |
| `run`/`runMany` `parent` argument | a previously returned image uuid | Yes, follows the above. |
| `snapshot` `dir` | caller (temp checkout dir) | Normalized to `checkout-N` by `replay-repository.ts:76-96`. |
| `cmd` / `commands` | caller, derived from diagnosis + policy + proposal | Deterministic given the same provider responses. |
| `options.operationId` | caller, `repair-tools.ts:167-169` = `${nodeId}-op-${NNN}`; `nodeId` from `search.ts:118-120` = `search-NNN` | **Deterministic and unique per logical call.** |
| `options.timeoutSec` | `Math.min(const, budget.remainingElapsedTimeSec())`, `repair-tools.ts:162-165` | Stable in practice (30/120); clock-derived only near budget exhaustion. |
| `cancel(operationId)` argument | caller | Deterministic string, but whether and how often it is called is racy. |
| `operationCapacity()` | no arguments | Interchangeable records; only the **count** matters. |

**So option (b), an id-rename map, solves a problem that does not exist here.** Replayed ids already
equal recorded ids. Discard it.

### (a) Canonical request fingerprint + first unconsumed match — recommended

Key each executor record by `canonicalJson([method, normalizedArgs])` and keep a
`Map<fingerprint, RecordedExecutorCall[]>` of unconsumed records; `next()` shifts the first entry
under the live call's fingerprint, else fails with the same `ReplayMismatchError` shape.

Why it fits this codebase unusually well:

- Every concurrent-window executor call already carries a globally unique, deterministic
  `operationId` (`search-001-op-002`), so fingerprints are distinct across branches. In bundle
  33949944171 the six racing `run` calls have six distinct operationIds.
- Serial-phase calls (`importImage`, the two `snapshot`s, the setup/triage/reproduction runs, the
  post-search verification run at sequence 22) carry no `operationId` but have distinct commands or
  distinct parents, so their fingerprints are distinct too. The two `runMany` calls at sequences 7
  and 8 differ by `SUTURA_TRIAGE_ATTEMPT='0'` vs `'2'`.
- The change is entirely consumption-side. No stored bundle bytes change, so no `bundleSha256` and
  no captured-fixtures manifest entry is invalidated.

Trade-offs and what it does **not** fix:

- **Weakened ordering guarantee.** A genuine regression that reorders serial work would no longer
  be caught. Mitigation: keep strict ordering as the default and relax it only for records that
  carry an `operationId` (plus `cancel` and `operationCapacity`), or only when the previous strict
  match failed. A two-tier matcher — try the positional record first, fall back to fingerprint
  lookup — preserves the current error messages for the common case and only relaxes under
  concurrency.
- **`operationCapacity` needs a special rule.** It has empty args, so all its records share one
  fingerprint. Matching any unconsumed one is fine, but the **count** varies with scheduling: 3
  records in 33949944171, 9 in 33321106629, because `availableBranches` probes at `search.ts:105`,
  `search.ts:113` and `heal.ts:1051` depend on batch shape. `assertConsumed`
  (`recorded-call-cursor.ts:77-88`) will then fail on leftovers. Either exempt `operationCapacity`
  from `assertConsumed` (the way ConTree HTTP is exempt today), or stop recording it and serve it
  from a single recorded capacity value in `configuration`.
- **`cancel` is worse than out-of-order — it is conditional.** In 33949944171 the race at
  `search.ts:142-149` fired and produced four `cancel` records plus one recorded
  `ConTree operation ended with CANCELLED` error at sequence 17. Whether that race fires at all
  depends on which branch settles first and whether the others are already `settled[]`. Under any
  replay the set of `cancel` calls may legitimately differ from the recording. Fingerprinting does
  not fix a *set* difference. Practical mitigation: treat `cancel` records like ConTree HTTP —
  serve any unconsumed matching record, synthesize a benign
  `{operationId, requested: false}` when none is recorded, and exempt them from `assertConsumed`.
  Document that cancellation evidence is observational, not a replay contract.

### (b) Group by operation, match by arguments with an id-rename map

Not applicable, per the id table above: replayed image ids are identical to recorded ones, so there
is nothing to rename. If it were adopted anyway, it would add a stateful rename map whose only
effect is to *mask* genuine id divergence, which is a fail-open change. Recommend against.

### (c) Serialize the pipeline under replay

Thread a `replay: true` flag into `heal` and force `concurrencyCapacity` to 1 at
`heal.ts:976-981` (the branch already exists — it returns 1 when `ctx.search === undefined`).

- **Pro:** conceptually the cleanest; restores a single deterministic order and keeps strict
  positional matching everywhere.
- **Fatal con for existing bundles:** it changes *which* calls happen, not just their order. With
  `concurrency = 1` the batch at `search.ts:115` has size 1, so `cancellationStarted` at
  `search.ts:142` can never fire and `options.cancel` is never called. Bundle 33949944171's four
  `cancel` records and its cancelled-operation error at sequence 17 would be permanently
  unconsumable, and `assertConsumed` would fail. Worse, `search.ts:194` breaks out of the batch loop
  as soon as any child passes, so branches 003 and 004 would never expand at all and their recorded
  `run` calls would also go unconsumed.
- It would only work for bundles recorded *after* the pipeline was made serial, which means
  discarding every existing complete capture and paying for new live runs. Given the freeze rule in
  `.claude/rules/ci-parity.md` about paid live runs, that is expensive.
- A variant worth noting: keep concurrency but make the *scheduler* deterministic under replay by
  awaiting each branch's provider turn through a replay-aware barrier that releases branches in
  recorded issue order. That preserves the call set but adds a replay-only code path inside the
  production scheduler, which is exactly the kind of divergence replay exists to detect.

### (d) Per-branch cursors — a targeted middle ground

Partition `bundle.executor` by branch: records whose `args[2].operationId` (for `run`/`runMany`) or
`args[0]` (for `cancel`) begins with `search-NNN` go to that branch's cursor; records with no
attribution stay on a shared serial cursor. Within a branch, order is strictly deterministic
(`repair-tools.ts:166` increments `operationIndex` monotonically), so each per-branch cursor can stay
positional and keep its exact error messages. Across branches nothing is ordered.

- **Pro:** preserves strict ordering where it is meaningful, needs no schema change (the branch id is
  already inside the recorded args), and gives sharper errors than a global fingerprint map
  ("branch search-003 expected op-002, received op-003").
- **Con:** it hardcodes knowledge of the `search-NNN-op-NNN` naming convention into the replay layer,
  coupling `packages/core/src/replay` to `packages/core/src/engine`. It shares option (a)'s
  `operationCapacity` and `cancel` problems unchanged.
- In practice (a) and (d) are the same mechanism with different key functions; (a) with a two-tier
  fallback is simpler to implement and to explain.

### Recommendation

Implement (a) as a **two-tier match inside `RecordedCallCursor`**: try the record at the current
index first, and only on mismatch fall back to a fingerprint lookup among unconsumed records. Add
the `operationCapacity` and `cancel` exemptions described above. That fix is consumption-side only,
so no bundle bytes, hashes, manifest entries, or downstream consumers change. Then add executor
coverage that is currently missing: a test that a reordered executor stream still replays, and a
test that a stream with a genuinely different `cmd` or a missing branch still fails closed.

Separately and independently: route `replay-fetch.ts`'s content mismatches through
`RecordedCallCursor.fail` so `rethrowMismatch()` at `replay-orchestrate.ts:149` can surface them,
instead of letting `classify.ts:200` turn a precise `ReplayMismatchError` into
`Diagnosis model request failed`.

## Verification after the fix (2026-09-05)

The two-tier executor cursor (positional first, then an exact match among unconsumed executor records; capacity probes and cancellations observational) was applied both to the candidate and, for verification, onto a throwaway checkout of the v0.2.0 release commit `a943ded4`, the version the Case Lab workflow replays with. Both live Case Lab bundles (`sutura-replay-33949944171.json`, `sutura-replay-33951048947.json`) now replay their entire executor stream. The exchange 14 mismatch is gone.

Both then stop at exchange 21, the posted report body, at the search table: the live run recorded `search-003` and `search-004` as `cancelled` because the batch race fired when `search-001` passed, while the replay, whose provider turns resolve from memory, scheduled the batch differently and recorded `frontier` and `failed`. That is the scheduling dependence of cancellation and capacity probes described in section 7: the call set differs, not only its order, so no consumption-side matcher can make the report byte-identical. Making the replayed search follow the recorded schedule (recorded capacity answers in recorded positions, recorded cancellations honored, unrecorded expansions skipped) is a design decision on the production scheduler and is filed as an issue rather than patched here.

The captured dogfood bundle `33323765566` shows the same shift: its replay used to end with an HTTP `sequence exhausted` at 108 because a swallowed executor mismatch sent the pipeline into extra provider turns; it now replays its executor stream and stops at port sequence 18 on report-body drift, the same class as its sibling `33321106629` at 17.
